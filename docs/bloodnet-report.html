The pitch, in about a minute

BloodNet connects blood banks and hospitals. When a donation is recorded it becomes three units (red cells, platelets, plasma), and each one gets its own expiry date. A hospital searches for nearby banks that hold compatible stock and raises a request. Bank staff allocate units to it, and that allocation stays correct when many people allocate at once: a test runs 50 parallel allocations against real MySQL and checks that no unit goes to two requests. Banks can move stock between each other through a transfer workflow. Background jobs expire old units, release reservations nobody collected, and suggest moving near-expiry units to banks that are short.

Getting the first admin in

  1. On startup, if ADMIN_EMAIL and ADMIN_PASSWORD are set and that email isn't registered, the app creates that admin account.
  2. Other admins can use Create admin account on the login page. It only appears when ADMIN_SIGNUP_CODE (12+ characters) is set on the server, and the form needs that code. A wrong code returns 403.
  3. Once signed in, the admin adds bank staff and hospital users from the Users page. There is no public sign-up for those roles.

1. Donation becomes stock

  1. Staff register a donor (name, group, date of birth, phone). Phone is unique.
  2. Staff record a donation. The donor row is locked with SELECT … FOR UPDATE so two people can't record two donations at the same moment.
  3. Rules checked: age 18–65 and at least 90 days since the last donation. A failure returns 422 with the reason and the next eligible date.
  4. Inventory creates one unit per component. Expiry is collection time plus shelf life: red cells 42 days, platelets 5, plasma 365.

The strongest interview story

Allocation under load

AllocationService.allocate() runs at READ_COMMITTED and does three things:

  1. Lock the request row (@Lock(PESSIMISTIC_WRITE) → SELECT … FOR UPDATE). Two people allocating the same request run one after the other; the second sees it's already RESERVED and gets a 409.
  2. Lock free units with SKIP LOCKED. One query per compatible group, exact group first, ordered by expiry. Rows another transaction holds are skipped instead of waited on.
  3. Reserve and record: units become RESERVED for 2 hours, request_allocation rows are written, the request counters are updated, commit.
SELECT id FROM blood_unit
WHERE bank_id = :bankId AND component_type = :component
  AND status = 'AVAILABLE' AND blood_group = :group AND expires_at > :after
ORDER BY expires_at, id
LIMIT :limit
FOR UPDATE SKIP LOCKED

Index idx_unit_alloc (bank_id, component_type, status, blood_group, expires_at) returns rows already in expiry order, so InnoDB stops after LIMIT rows and locks only those.

What the test caught. The first version picked units in one query with ORDER BY (blood_group = :preferred) DESC, expires_at. That expression forces a filesort, and InnoDB locks every row it reads before sorting. The first transaction locked all 60 matching units, and the other 49 skipped all of them. Only 3 of 60 units were reserved. Splitting it into one indexed query per blood group fixed it: 60 of 60.

Self-annealing log

Problems we hit and how they were fixed

Each one was found by running the code or the tests, fixed, re-tested, and written down in docs/decisions.md.

concurrencyOnly 3 of 60 units reserved under 50 parallel requests
CauseAn ORDER BY on an expression forced a filesort; InnoDB locked every matching row before LIMIT, so the other transactions skipped them all.
FixOne query per blood group, ordered by the indexed expires_at. Now 60 of 60.
time zonesExpired reservations were not released
CauseThe test DB URL had no connectionTimeZone=UTC. Plain JDBC wrote IST, Hibernate wrote UTC: 5 h 30 apart.
FixUTC parameters on the test URL, and the app sets the JVM zone to UTC at startup.
toolingTestcontainers said "Docker not available"
CauseDocker Engine 29 raised its minimum API version, which Testcontainers 1.20 didn't handle.
FixPinned testcontainers.version to 1.21.4 in the pom.
databaseEVENT_PUBLICATION doesn't exist
CauseSpring Modulith's MySQL SQL uses upper case, and MySQL on Linux has case-sensitive table names.
FixCreated the table as EVENT_PUBLICATION in V1.
SpringTwo CorsConfigurationSource beans
CauseSpring MVC registers one too, so injecting by type was ambiguous.
Fix.cors(Customizer.withDefaults()), which picks our bean by name.
AOP"JoinPointMatch was NOT bound" in the audit aspect
CauseAt HIGHEST_PRECEDENCE it ran before Spring's ExposeInvocationInterceptor.
FixOrder HIGHEST_PRECEDENCE + 100: still outside @Transactional.
AngularTemplate name clash and @let
CauseThe #nav template ref hid the nav() signal; @let only exists from Angular 18.1.
FixRenamed the signal to menu(); replaced @let with component methods.
